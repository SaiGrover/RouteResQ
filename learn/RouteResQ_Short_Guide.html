RouteResQ

RouteResQ in short

The whole project in a few pages, in very easy words. CN Lab 24B15CS313 · JIIT Noida · live at routeresq.streamlit.app

IN ONE SENTENCE
RouteResQ finds out why a network failed, what it did to the traffic and whether it recovered, and it honestly says how sure it is, using only real evidence.

02The problem

"The website is not opening" can mean many things: DNS failed, the host is down, the path is broken, a link failed, the network is jammed, the port is closed, or the certificate is bad. Ping and traceroute only show the symptom ("no reply"), not the cause. They can even mislead: many servers ignore ping on purpose.

THINK OF IT LIKE
A fever is a symptom. A good doctor runs a few tests, looks at them together, and says "most likely flu", or "I need one more test". RouteResQ is that doctor for networks.

03The five stages (the buttons on top of the app)

01 DetectWhat failed? Run real checks.
02 DiagnoseWhy, and how sure are we? 17 rules decide.
03 ImpactWhat did it do to the traffic? Count every packet in NS2.
04 RecoveryDid it come back? Detour, wait for repair, or never.
05 ReportCan we prove it? Everything saved to files and reports.

04Four working parts

1 · Live checks

Real DNS, gateway ping, ping, traceroute and TCP connect on the real computer.

2 · Rule engine

17 if-then rules turn the results into findings and possible causes.

3 · NS2 experiments

Break a link or jam it on purpose in a 6-node network; measure every packet.

4 · Transport lab

Real TCP, UDP and TLS on loopback, broken in 6 ways and repaired.

A root-cause register joins them: one row per failure, its cause and how sure we are.

05Honest words, no fake percentages

StatusWhen
Confirmed (injected)We caused the fault ourselves (NS2 or a drill), so we know it.
LikelyLive check: exactly one explanation fits all the evidence.
Not confirmedLive check: several explanations fit. We list them all, with the next check.
No failure detectedEverything was healthy.

A live failure can never be "Confirmed", because we did not cause it. Like a detective: if you hid the key, you know where it is; if someone else lost it, you can only say "likely".

06Part 1: the live check

  • Safety first: only allowed destinations (e.g. 8.8.8.8, localhost, your own network, and two safe test targets: nonexistent.invalid and 192.0.2.1). Everything else is refused.
  • Steps: look at my network → DNS lookup → ping the gateway → ping the destination → traceroute → TCP connect (optional).
  • Gateway trick: gateway works but destination fails → the problem is beyond your house.
  • Safe commands: only 7 programs, no shell, time limits. Output is read by parsers that never guess values.

07Part 2: the rule engine

A rule is an "if this, then that" sentence. Same input → same answer, no machine learning. Main rules:

  • DNS failed → DNS Resolution Failure.
  • 0 ping replies → Unreachable. But if TCP or traceroute shows the host is alive → contradiction ("ping is probably blocked").
  • Loss ≥ 5% → Packet Loss. Delay > 150 ms or jitter > 30 ms (with 3+ replies) → High Latency.
  • Congestion needs 2 signs together (more delay, more loss, more jitter, less throughput than the saved "normal" run). One sign alone is not enough.
  • Route changed if the same hop answers from a different address than last time.

Every answer comes with a rule trace: all 17 rules, whether each fired, and why.

REAL EXAMPLES
8.8.8.8: replies came back → No failure detected
nonexistent.invalid: DNS said "not found", gateway worked → Likely name does not exist
192.0.2.1: gateway OK, 0/4 replies, path silent after hop 2, TCP timed out → Not confirmed (host off, path broken, or firewall: all fit)

  • B1: routers sent 14 warning messages in 0.5 s and switched to n3 at once. Only 2 packets (already on the broken wire) were lost; all 375 sent during the break arrived.
  • B2: n1 kept sending into the dead link. 0 of 375 arrived. 375 were thrown away silently (NS2 wrote no drop line) + 2 dropped on the wire.
  • C: the queue filled to 20 at 3.30 s; delay rose 33.6 → 102.75 ms; 170 drops (117 ours). The queue emptied 0.143 s after the extra traffic stopped, then 0% loss again.
HOW WE READ THE NS2 DIARY
The trace file has one line per event: + joined a queue, - left it, r received, d dropped. Each packet has a unique ID, so we follow it like a parcel tracking number. "Sent" is counted only at n0 and "received" only at n5 (no double counting). Every packet gets one fate: delivered, dropped at a full queue, dropped on a broken link, lost at a node, lost on a link, or still in flight. Following IDs is how we found B2's 375 silent losses.

B1 vs B2 lesson: same failure, different routing. Smart routing = a hiccup; fixed routing = an outage.

10The root-cause register

13 rows: 3 live checks + 4 NS2 scenarios + 6 drills. 11 failures have a stated cause; 2 are healthy (8.8.8.8 and A). Live rows are re-checked with the current rules every time.

11The app, the code, the tests

  • App: Streamlit website with 8 pages: Overview, Diagnostics, Root cause, NS2 simulation, Recovery, TCP·UDP·TLS lab, Reports, and a Guided demo that runs the whole story in 6 steps.
  • Golden rule: the website has no networking logic. Pages call the backend, the backend saves files (JSON, CSV, Markdown), pages read them back. No database.
  • Code: about 9,900 lines of Python in folders with one job each: diagnostics/, failure_analysis/, simulation/, analysis/, communication/, security/, app_pages/, ui/.
  • Tests: 159 pytest tests, including real NS2 runs, real sockets and every app page.
  • Online: Streamlit Cloud installs real NS2 via packages.txt. On Windows, NS2 runs in Docker.
  • Safety: allow-list of destinations, no shell, only 7 programs, strict checks on NS2 settings, standard TLS only.

12Limits

  • Live checks only see what devices answer (firewalls block ping), so live causes are at best "Likely".
  • NS2 results describe our model, not a real network; NS2's DV reacts faster than real protocols.
  • Loopback has no real distance. RouteResQ explains failures; it does not repair real networks.

14Top questions

Why not just use ping?
Ping shows a symptom. "No reply" can mean host off, path broken or ping blocked. We combine five checks to tell them apart.
Why is a live cause never "Confirmed"?
We did not cause it. Only in NS2 and the drills do we know the cause, because we injected it.
Why are B1 and B2 so different?
Same failure. DV finds the backup road in 43.6 ms (2 lost). Static keeps using the dead link (377 lost, 3.024 s gap).
How did you find B2's losses with no drop lines?
We follow every packet by its ID. 375 reached n1 and were never seen again.
How do you prove congestion in C?
2.5 Mb/s into a 2 Mb/s link, queue full at 20, 170 drops on a working link, delay 33.6 → 102.75 ms; back to normal after the queue emptied.
