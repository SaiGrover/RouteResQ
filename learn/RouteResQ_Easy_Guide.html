PART A

Networking from zero

Fifteen short lessons. Each one is an idea that RouteResQ uses. By the end of Part A you will understand every word in the project.

01What is a computer network?

A network is a group of computers joined together so they can send messages to each other. The internet is the biggest network of all: millions of smaller networks joined together.

When you open a website, your laptop sends a message ("please give me this page") to another computer far away, called a server. The server sends the page back. That is all a network does: carry messages from one computer to another.

THINK OF IT LIKE

The postal system. Your laptop writes a letter, puts an address on it and drops it in the post. Post offices pass it along until it reaches the right house. The house writes back the same way.

Most of the time this works perfectly. But sometimes the letter never arrives, arrives late, or comes back saying "no such address". RouteResQ is a project about those bad days: finding out what went wrong, and why.

02Packets: big messages are cut into small pieces

Computers do not send a big file in one go. They cut it into many small pieces called packets. Each packet travels on its own and is put back together at the other end.

A file is cut into packets, each packet travels on its own, and the receiver puts them back together.
THINK OF IT LIKE

Sending a 500-page book by post as 500 separate envelopes, each with a page number written on it. If one envelope is lost, you only resend that one page, not the whole book.

In RouteResQ's simulation, every packet is 1000 bytes (8000 bits). A packet that never arrives is called a lost packet. Counting lost packets is a big part of the project.

03Addresses: IP address and port

Every computer on a network has an IP address, a number like 8.8.8.8 or 192.168.1.1. Packets carry the IP address of where they are going, just like a letter carries a house address.

One computer runs many programs at once (a browser, a game, WhatsApp). So a packet also carries a port number, which says which program should get it. Websites usually use port 80 or 443.

THINK OF IT LIKE

The IP address is the address of a big apartment building. The port is the flat number inside it.

Some special addresses appear again and again in this project:

AddressWhat it is, in simple words
8.8.8.8Google's public DNS server. It almost always answers, so it is our "healthy" test.
127.0.0.1"Myself". Packets sent here never leave your own computer (lesson 14).
192.168.x.xA private home or office address, like your Wi-Fi router.
192.0.2.1An address that is reserved for examples in books (rule RFC 5737). No real computer uses it, so nothing ever answers. We use it to show an "unreachable" failure safely.
nonexistent.invalidA name that can never exist (rule RFC 6761). We use it to show a "name not found" failure safely.

04DNS: the phonebook of the internet

People remember names like dns.google. Computers need numbers like 8.8.8.8. DNS (Domain Name System) is the service that turns a name into a number. This is called resolving the name.

You give DNS a name; it gives you back the IP address.
THINK OF IT LIKE

The contacts list on your phone. You tap "Mom", and the phone looks up her number for you. If the name is not in the list, you cannot call at all.

If DNS fails, nothing else can happen: no address means no packet can even be sent. When a name does not exist at all, DNS answers NXDOMAIN ("no such domain"). On Windows you see this as "host not found" or error 11001.

05Routers, links, paths and hops

Your packet does not jump straight to the server. It passes through many routers on the way. A router is a box that looks at the packet's address and sends it one step closer to where it is going.

  • A link is the wire (or Wi-Fi, or fibre) between two devices.
  • A path or route is the full chain of routers and links a packet takes.
  • Each router on the path is one hop. "The server is 10 hops away" means 10 routers are in between.
A packet hops from router to router. The first router is your gateway.
THINK OF IT LIKE

Driving across a city. The roads are links, the crossings are routers, and the route is the list of crossings you pass. At each crossing a signboard (the router) tells you which way to turn.

06The gateway: the first door out

The default gateway is the first router your computer talks to. At home it is usually your Wi-Fi router (often 192.168.1.1). Every packet going to the internet goes through it first.

The gateway is very useful for finding problems. If your computer cannot even reach the gateway, the problem is close to you (your Wi-Fi or cable). If the gateway answers but the far server does not, the problem is further away.

REMEMBER

"Gateway works, destination fails" means the problem is beyond your house. RouteResQ always tests the gateway for exactly this reason.

07Ping: "Are you there?"

Ping is a tiny test. Your computer sends a small packet (an ICMP echo request) and the other computer replies (an echo reply). Ping tells you two things:

  • Did the reply come back? If 4 are sent and 4 come back, there is 0% loss.
  • How long did it take? The time for the trip there and back is the RTT (round-trip time), in milliseconds (ms). 1 ms is one-thousandth of a second.
THINK OF IT LIKE

Shouting "Hello?" into a valley and timing the echo. A quick echo means the wall is close; no echo means… something. Maybe there is no wall, maybe the wind took your voice. You cannot tell which.

WATCH OUT

Many servers and firewalls ignore ping on purpose for safety. So "no ping reply" does not always mean the computer is down. This one fact is why RouteResQ never trusts ping alone.

08Traceroute: "Which roads did we take?"

Traceroute (called tracert on Windows) shows the list of routers between you and the destination, one hop at a time.

How does it work? Every packet carries a number called TTL (time to live). Each router subtracts 1 from it. When it reaches 0, the router throws the packet away and sends back a note saying "it died here". Traceroute sends packets with TTL 1, then 2, then 3, and so on. Each note reveals the next router on the path.

If a router does not answer, traceroute prints * (a star) for that hop. Many stars in a row at the end mean the packets go quiet after a certain point.

THINK OF IT LIKE

Sending a friend down the road with a rule: "Walk 1 crossing and call me. Now walk 2 crossings and call me. Now 3…". Each phone call tells you one more crossing on the route.

09The four health numbers

When a network is "slow" or "bad", we can measure four things. Learn these four words; they appear everywhere in RouteResQ.

WordSimple meaningEveryday picture
Delay (latency)How long one packet takes to arrive. For ping, the round trip (RTT).How long a courier takes to deliver.
Packet lossThe share of packets that never arrive, as a percentage.Out of 100 letters, 5 never arrive = 5% loss.
JitterHow much the delay keeps changing from packet to packet.A bus that comes in 5 minutes, then 20, then 2. Unreliable.
ThroughputHow much data actually arrives per second (kb/s, Mb/s).How many litres of water come out of the pipe per second.

Also useful: bandwidth is the most a link can carry (the pipe's size). Throughput is what actually got through. Mb/s means megabits per second (1 Mb/s = 1,000,000 bits each second).

10Queues and congestion: the traffic jam

Every router has a small waiting line called a queue (also called a buffer). If packets arrive faster than the outgoing link can send them, they wait in the queue. If the queue is full, new packets are simply thrown away. Throwing away the newest arrival when the queue is full is called DropTail.

Congestion is when more traffic arrives than a link can carry. Signs of congestion: delay goes up (packets wait in the queue), and loss goes up (the queue overflows).

More comes in than can go out: the queue fills up, waiting time grows, and extra packets are dropped.
THINK OF IT LIKE

A toll booth on a highway. If cars arrive faster than the booth can serve them, a line forms (delay). If the line becomes too long to fit, new cars are turned away (loss).

11When a road breaks: link failure and routing

A link failure is when a wire between two routers stops working (cut cable, broken port, power cut). Packets sent onto that link are lost.

What happens next depends on routing: the way routers decide which path to use.

smart

Dynamic routing (Distance Vector, DV)

Routers keep talking to their neighbours: "I can reach X at this cost". When a link breaks, they tell each other at once and switch to another path. Traffic finds a detour.

fixed

Static routing

Routes are set once at the start and never change. When a link breaks, routers keep sending packets into the broken link. Traffic stops until the link is repaired.

Each link has a cost. Routers prefer the path with the lowest total cost. In RouteResQ, the main path costs 2 and the backup path costs 6, so the backup is used only when the main path breaks.

THINK OF IT LIKE

A road is closed. A driver using Google Maps (DV) gets a new route in seconds. A driver following a printed map from last year (static) keeps driving to the closed road and waits there until it reopens.

12TCP and UDP: two ways to send

Once a packet can reach the other computer, programs need rules for talking. The two most common sets of rules (protocols) are TCP and UDP.

TCPUDP
Starts with a handshake?Yes: SYN, SYN-ACK, ACK ("hello", "hello back", "great, let's talk")No, just starts sending
Lost packets?Sent again automaticallyGone forever
Order?Always in the right orderMay arrive mixed up

Two more TCP words: if you knock on a port where no program is listening, the computer answers with a RST (reset), meaning "nobody here". This is called a refused connection. If nothing answers at all, you get a timeout.

REMEMBER

A "refused" reply is actually good news about the computer: it is switched on and answering. Only that one program is missing.

13TLS: the sealed, signed envelope

Normal TCP is like a postcard: anyone on the way could read it. TLS (the "S" in HTTPS) adds three protections:

  • Secrecy: the data is encrypted (scrambled), so only the receiver can read it.
  • Identity: the server shows a certificate, a digital ID card that says "I really am localhost".
  • Trust: the certificate is signed by a CA (Certificate Authority), someone the client already trusts, like a government that issues passports.

The client checks two things before sending any data: is the ID card signed by someone I trust (the chain)? And does the name on the card match the server I wanted (the host name)? If either check fails, the connection is stopped.

SHA-256 is a "fingerprint" for data. Any file gives a 64-character fingerprint; change even one letter in the file and the fingerprint is completely different. If the sender's and receiver's fingerprints match, the file arrived without any change.

THINK OF IT LIKE

A bank courier. You check their ID card (certificate), you check the card was issued by the bank (CA), you check the name matches (host name), and you weigh the parcel before and after to make sure nothing was taken out (SHA-256).

14Loopback: talking to yourself

The address 127.0.0.1 (also called localhost) is the loopback address. Packets sent to it never leave your computer; they go out of one program and straight into another on the same machine.

Why is this useful? Because we can run a real server and a real client on one laptop, break the connection on purpose, and watch what happens, without bothering anyone else's network. RouteResQ's transport lab (Part 4) works this way.

15Simulation and NS2: a practice network inside the computer

We cannot go and cut a real internet cable to see what happens. So we use a simulator: a program that pretends to be a network. It creates fake routers and links, sends fake packets, and follows every rule of real networks.

NS2 (Network Simulator 2, version 2.35) is the simulator used in our Computer Networks course. You describe the network in a small script written in a language called Tcl: how many nodes, which links, how fast, what traffic, and what to break and when. NS2 runs it and writes a trace file: a diary with one line for every single thing that happens to every packet.

THINK OF IT LIKE

A flight simulator. Pilots practise engine failures in a simulator because they cannot practise them on a real plane full of people. We practise link failures in NS2 for the same reason.

REMEMBER

In a simulation we cause the problem ourselves, at an exact time. So we know the true cause. This is the key difference from a real, live network, where we can only guess.

PART B

The RouteResQ project

Now that you know the words, here is the project itself: what problem it solves, its four working parts, and how each one works inside.

16The problem RouteResQ solves

A user says: "The website is not opening." That one sentence can have many different causes:

Possible causeWhat really happened
DNS failureThe name could not be turned into an address, so nothing was sent.
Host or path downPackets disappear somewhere after the last router that answers.
CongestionQueues are full; packets wait long or get dropped.
Link failureA wire broke; traffic needs a detour or stops.
Port closedThe computer is on, but the program is not running.
Bad certificateTLS refused to talk because the ID card was wrong.

Normal tools like ping and traceroute only show symptoms ("no reply"), not causes. And they can mislead: a server can ignore ping but still work perfectly. So people guess a cause and say it with too much confidence.

THINK OF IT LIKE

A fever is a symptom. It could be flu, an infection or heat stroke. A good doctor runs a few tests, looks at all the results together, and then says "most likely flu", or "I need one more test to be sure". RouteResQ is that careful doctor, for networks.

RouteResQ IN ONE SENTENCE
RouteResQ finds out why a network failed, what the failure did to the traffic, and whether service came back, and it honestly says how sure it is about each answer, using only real evidence.

17RouteResQ in one picture: the five stages

Every failure goes through the same five questions. These five stages are also the buttons along the top of the app.

01

Detect: what failed?

Run real checks (DNS, ping, traceroute, TCP) and collect what happened.

02

Diagnose: why, and how sure are we?

17 rules read the results and list possible causes, each with an honest certainty word.

03

Analyse impact: what did it do to the traffic?

In NS2, count every lost packet, measure the delay and throughput, and see if the route changed.

04

Observe recovery: did service come back, and how?

Did traffic take a detour, wait for the repair, or never recover?

05

Report: can we prove it?

Write everything to files and reports so anyone can check every number.

To do this, the project has four working parts:

part 1

Live diagnostics

Runs real DNS, ping, traceroute and TCP checks on the computer the app runs on.

part 2

Rule engine

17 if-then rules that turn the raw results into findings and possible causes.

part 3

NS2 simulation

Breaks a link or overloads it on purpose in a 6-node network and measures every packet.

part 4

Transport lab

Real TCP, UDP and TLS on loopback, broken in six controlled ways, then repaired.

A root-cause register joins all four: one table row per failure, its cause and how sure we are. Everything is shown in a website built with Streamlit and saved to plain files.

18Three kinds of evidence

RouteResQ gets its evidence from three different places. They are never mixed, and every page and report says which one a result came from.

WhereWhat it isDo we know the true cause?Best possible status
Live measurementReal commands on the real computerNo. We only see what devices choose to answer.Likely
NS2 simulationReal NS2 runs with a fault we injectedYes. We created the fault.Confirmed (injected)
Loopback socketsReal TCP/UDP/TLS on one computer, with faults we injectedYes. We created the fault.Confirmed (injected)
THINK OF IT LIKE

A detective. If you hid the key yourself, you can say for sure where it is ("confirmed"). If someone else lost it, you can only say where it is most likely to be, based on clues ("likely").

REMEMBER

A live failure is never marked "Confirmed", because we did not cause it. A simulated cause is never presented as the cause of a real problem.

19Honest words: how sure are we?

RouteResQ never prints fake percentages like "87% sure". There is no real data to calculate such a number, so it would be made up. Instead it uses words with clear meanings.

The four cause statuses (in the register)

StatusWhen it is used
Confirmed (injected)We caused the fault on purpose (NS2 or a drill), and its effect is visible in the evidence.
LikelyLive check where exactly one explanation fits all the evidence.
Not confirmedLive check where several explanations fit. We list them and the checks that would tell them apart.
No failure detectedEverything was healthy. Nothing to explain.

The four evidence levels (on every finding)

LevelSimple meaning
confirmedWe saw it directly in the output. ("0 of 4 replies came back.") This is a fact, not a cause.
likelyThe explanation that fits all the evidence best.
possibleFits the evidence, but other explanations also fit.
insufficient evidenceNot enough data to say anything (for example, fewer than 3 replies).

The six honesty rules built into the code

  • No confidence percentages.
  • No made-up data: every number comes from a stored result. If something could not be measured, it shows "n/a".
  • Contradictions are shown, never hidden (for example "ping failed but TCP worked").
  • Recovery is claimed only when the trace actually shows it.
  • Old stored results are labelled "stored", never passed off as fresh.
  • Only allowed destinations can be tested.

20Part 1: the live check, step by step

This part lives in the diagnostics/ folder. You type a destination (like 8.8.8.8) and press Run. Here is everything that happens.

Step 0: is this destination allowed?

Testing other people's networks without permission can be illegal. So before sending even one packet, RouteResQ checks an allow-list (config/authorized_targets.json):

  • Always allowed: the two safe test targets nonexistent.invalid and 192.0.2.1.
  • Listed hosts: localhost, 8.8.8.8, 1.1.1.1, 9.9.9.9, dns.google, one.one.one.one, example.com, github.com.
  • Your own computer (127.x) and your own home network (private addresses). On the public website, private addresses are blocked, because there they would be the hosting company's internal network.
  • Everything else is refused. Input starting with - is refused too, because -n 100 would trick ping into reading it as an option.

Step 1 to 7: the checks

1

Start a run

Give it a random 12-character ID, the time, and the options (how many pings, timeout, max hops).

2

Look at my own network

Find the computer's name, its IP address, its default gateway (from the route table) and its DNS servers.

3

DNS lookup

Turn the name into an address and time it. If it fails, record why: nxdomain (name does not exist), temporary (DNS did not answer in time), no_data or other.

4

Ping the gateway

Up to 4 pings to the first router. This separates "my network is broken" from "the far end is broken".

5

Ping the destination

With the chosen count and timeout. Gives replies, loss % and RTT.

6

Traceroute

Only if DNS worked. Lists the hops and shows where the path goes quiet.

7

TCP connect (optional)

Try to open a TCP connection on a port. Result: connected, refused (computer is up), or timeout.

How commands are run safely

  • Only seven programs can ever run: ping, tracert, traceroute, tracepath, route, ip, ipconfig.
  • They are run without a shell, as a list of words. So tricks like ; delete everything do nothing.
  • Every command has a time limit. A missing tool gives a clear message instead of a crash.
  • Windows and Linux print different text, so the project has a parser for each. A parser is code that reads the messy text output and pulls out the numbers. If a line cannot be understood, it is skipped and a warning is recorded. Values are never guessed.
EXAMPLE OF CAREFUL PARSING

Windows counts "Destination host unreachable" messages as "Received" in its ping summary. That is misleading: no real reply came back. RouteResQ counts only genuine echo replies, and adds a note explaining the difference. Also, Windows prints time<1ms for very fast replies; RouteResQ stores these as 0 ms with a warning.

History and baselines

Every run is saved as one line in results/diagnostics/history.jsonl. You can mark a healthy run as the baseline (the "normal" reference) for that destination. Later runs are compared with it: has the delay gone up? Has loss gone up? Has the route changed since last time?

21Part 2: the rule engine

This part lives in failure_analysis/rules.py. It reads the live results and decides what they mean.

A rule is a simple "if this, then that" sentence written in code. For example: "If the DNS lookup failed, then report a DNS Resolution Failure." There is no machine learning, no guessing; the same input always gives the same answer. That is called deterministic.

The limits the rules use (from config/thresholds.json)

SettingValueMeaning
High delay150 msAverage ping above this counts as high latency.
High jitter30 msDelay changing more than this is a lot of jitter.
Loss limit5 %Loss at or above this is reported as packet loss.
Minimum samples3Need at least 3 replies before judging delay.
Baseline delay1.5× and +20 msDelay is "worse than normal" only if both are true.
Baseline loss+10 pointsLoss rose at least 10 percentage points over normal.
Baseline jitter2×Jitter doubled compared with normal.
Throughput drop30 %Throughput 30% lower than normal.

All 17 rules in simple words

RuleIn simple words
R-DNS-01The name lookup failed → DNS Resolution Failure.
R-PING-00Ping output is missing or unreadable → note it; may lead to "Inconclusive".
R-REACH-010 ping replies (and DNS was fine) → Unreachable. But if TCP or traceroute shows the host is alive, report a contradiction instead ("ping is probably blocked").
R-REACH-02A router or the OS clearly said "unreachable / no route" → Unreachable, with that message as proof.
R-TCP-01The TCP connection timed out → Unreachable on that port.
R-LOSS-01Some (not all) pings lost, 5% or more → Packet Loss. With few pings it warns that one lost ping moves the % a lot (with 4 pings, 1 loss = 25 points).
R-LOSS-02All pings lost, nothing contradicts it → Packet Loss (complete).
R-LAT-01Average delay above 150 ms, with at least 3 replies → High Latency. Fewer replies → "not enough evidence".
R-LAT-02Jitter above 30 ms, with at least 3 replies → High Latency (unstable delay).
R-BASE-01Delay is 1.5× normal and 20 ms higher → High Latency compared with the baseline.
R-BASE-02Loss rose 10+ points over normal → one sign of congestion.
R-BASE-03Jitter more than doubled → one sign of congestion.
R-BASE-04Throughput 30% below normal → one sign of congestion.
R-CONG-01Two or more signs together, and at least one reply → Possible Congestion. One sign alone is not enough.
R-ROUTE-01Traceroute stops early, ping gets 0, TCP gets nothing → Possible Routing Issue.
R-ROUTE-02The same hop number answered from a different address than last time → route changed.
R-OK-01DNS fine, host answers, no failure found → Healthy / Reachable.
REMEMBER: WHY "TWO SIGNS" FOR CONGESTION?

One high delay can have many reasons: the server is far away, one router is slow, the server is busy. Calling it congestion from one sign would be a guess. Two signs together make it a fair "possible".

Contradictions: shown, never hidden

  • Ping fails but TCP connects → the computer is up; ping is probably blocked.
  • Ping fails but traceroute reaches it → ping may be blocked, or the loss was short.
  • Traceroute stops but ping works → routers are just not answering traceroute. Not a routing failure.
  • Gateway ignores ping but the destination answers → the gateway just ignores ping. Not a fault.

What the engine gives back

  • Observations: plain facts ("Ping: 0/4 replies, 100% loss").
  • Classifications: one or more of eight labels: Healthy / Reachable, DNS Resolution Failure, Unreachable Destination, High Latency, Packet Loss, Possible Routing Issue, Possible Congestion, Inconclusive.
  • Explanations: possible causes, each with evidence for, evidence against, and the next check that would confirm it.
  • A conclusion sentence in plain English.
  • A rule trace: a list of all 17 rules, whether each one fired, and why. So every answer can be checked.
EXAMPLE: 192.0.2.1 (A REAL RUN)

What was measured: the gateway answered 4 of 4 pings. The destination answered 0 of 4. Traceroute: the last router that answered was hop 2 (10.240.12.49), then 8 silent hops. TCP connect timed out.

What the rules said: Unreachable Destination, Packet Loss, Possible Routing Issue.

Why "Not confirmed": three explanations all fit: the host is switched off, the path after hop 2 is broken, or a firewall blocks the probes. Since nothing tells them apart, RouteResQ honestly lists all three instead of picking one.

EXAMPLE: nonexistent.invalid (A REAL RUN)

DNS said "host not found" ([11001] getaddrinfo failed). The gateway 192.168.1.1 answered, so the local network was fine. Result: DNS Resolution Failure, status Likely: "the name does not exist in DNS or is misspelt". Only one explanation fits, so it is "Likely".

22Part 3: the NS2 experiments

This part lives in simulation/ (running NS2) and analysis/ (reading the results). Here we break things on purpose and measure exactly what happens.

The map: six nodes

Packets go from n0 to n5. Normally they take the top road n0–n1–n2–n4–n5. The bottom road through n3 is the backup.
NodeJob
n0The source: the computer sending the data.
n1Entry router. This is where the road splits into top and bottom.
n2Top (main) core router.
n3Bottom (backup) core router.
n4Exit router, where the two roads join again.
n5The destination: the computer receiving the data.

Each link has a speed (bandwidth), a travel time (propagation delay), and a queue that holds up to 20 packets (DropTail). The backup links cost 3 each, so the top road (total cost 2) wins over the bottom road (total cost 6) while everything works.

The traffic

n0 sends a steady stream to n5 using CBR (Constant Bit Rate) over UDP: one 1000-byte packet every 8 ms, which is 125 packets a second, or 1 Mb/s. It sends from 1.0 s to 9.0 s, so 1001 packets in total. This is the "monitored" flow, flow 1.

The four experiments (scenarios)

NameRoutingWhat we break
A · healthyDVNothing. This is the "normal" reference for comparison.
B1 · link failure, DVDV (smart)Cut the n1–n2 link at 3.0 s, repair it at 6.0 s.
B2 · link failure, staticStatic (fixed)Exactly the same cut, but routing never reacts.
C · congestionDVAdd a second flow of 1.5 Mb/s from 3 s to 6 s. Now 2.5 Mb/s tries to fit into a 2 Mb/s link.

Every experiment is split into the same three time windows (phases): before (1–3 s), during (3–6 s) and after (6–9 s). This makes them easy to compare.

REMEMBER: WHY B1 AND B2?

They have the same failure; only the routing is different. So any difference in the results is caused by the routing alone. That is a fair experiment.

How a run happens

1

Check the scenario

Each scenario is a JSON file. Every value is checked strictly (only 20 known settings, correct units, no spaces or symbols), so nobody can sneak code into the Tcl script. This is called preventing Tcl injection.

2

Find NS2

If an ns program exists (Linux, the online app), use it. Otherwise use Docker with the image routeresq-ns2:2.35 (on Windows).

3

Run the Tcl script

routeresq.tcl builds the six nodes, the links, the traffic and the failure, and runs for 10 seconds of simulated time.

4

Save everything

The trace (out.tr), the event log, the scenario and run details go into a new folder under results/simulation/.

5

Analyse

Read the trace, rebuild every packet, measure everything, decide the recovery result, write the report.

23Reading the NS2 diary (the trace file)

The trace file has one line for every event. A line looks like this:

+ 1.0 0 1 cbr 1000 ------- 1 0.0 5.0 0 0
event time from to type size flags flow src dst seq packet-id

The first letter tells you what happened:

LetterMeaningPicture
+The packet joined a link's queueGot in the line at the toll booth
-It left the queue and started sendingPassed through the booth
rIt was received at the next nodeReached the next town
dIt was droppedTurned away

The last number is the packet ID. It is unique for each packet, so we can follow one packet across every hop, like a parcel tracking number.

Counting without cheating

A packet passes through 4 routers, so it shows up in the diary many times. If we counted every + as "sent", we would count each packet 4 times. So the rules are:

  • Sent = the first + at the source node only.
  • Received = an r at the destination node only.
  • Events at routers only add to the packet's path (for example 0-1-2-4-5).
  • Delay = time received − time sent.

Every packet gets exactly one "fate"

FateWhat it means
deliveredReached n5.
dropped_queueDropped (d) on a working link: the queue was full. This is congestion.
dropped_link_downDropped (d) on a link that was broken at that moment.
lost_at_nodeNo d line at all. The packet reached a router and was never seen again.
lost_on_linkNo d line; last seen on a link.
in_flightSeen in the last 0.5 s of the trace; it had no time to arrive yet. Not counted as lost.
THE FINDING WE ARE PROUDEST OF

NS2 2.35 has a quiet habit: when a router has no working route (in B2), it throws the packet away without writing any d line. A simple tool that only counts d lines would say "almost no loss" in B2. RouteResQ follows every packet by its ID, notices that 375 packets reached n1 and were never seen again, and reports them as lost_at_node. Without this, the worst failure would look fine.

24How we measure

The formulas in analysis/metrics.py, in simple words.

Loss % = lost packets ÷ (sent − still in flight) × 100
Delay = average of (time received − time sent) for delivered packets
Jitter = average change in delay between one packet and the next
Throughput = bits received at n5 ÷ length of the time window
  • Loss and delay are put into a phase by the time the packet was sent. Throughput is put into a phase by the time it was received.
  • Time series: the run is cut into 0.1 s slices, and each slice gets its own throughput, loss and delay. This draws the charts.
  • Queue length: rebuilt from + (joins), - (leaves) and d (dropped). The link with the biggest queue is the bottleneck.
  • Route change: only counted if the new path is used by at least 3 packets in a row. One odd packet is not a route change.
  • Delivery gap: a time with no arrivals at n5 longer than 50 ms while traffic is flowing. (5 × 8 ms = 40 ms, and the minimum is 50 ms.)
  • Routing messages: DV messages counted in 0.5 s slices, to see if routers "talked more" after the failure.

How recovery is decided

ResultWhen
ReroutedPackets sent during the failure still arrived, using a path that avoids the broken link.
Interrupted until restoredDelivery only started again after the link was repaired.
Not recoveredDelivery never came back before the end.
Recovered (congestion)After the queue emptied, packets had 0% loss and delay within 10% of "before".
Partially recoveredThe queue emptied but loss or delay did not fully return to normal.

Story A: a normal day (33.6 ms, explained)

Nothing breaks. All 1001 packets arrive, all on the top road 0-1-2-4-5. Every packet takes exactly 33.6 ms. Why that exact number? Two parts add up:

Travel time (propagation): 2 + 10 + 10 + 2 = 24.0 ms
Sending time (transmission): 0.8 + 4 + 4 + 0.8 = 9.6 ms
(8000 bits ÷ 10 Mb/s = 0.8 ms; 8000 bits ÷ 2 Mb/s = 4 ms)
Total = 33.6 ms

No waiting in queues, because 1 Mb/s fits easily into 2 Mb/s links.

Story B1: the road breaks, and traffic takes a detour

  • At 3.0 s the n1–n2 link breaks. DV routers immediately warn each other: 14 routing messages in the next 0.5 s, compared with about 2.4 normally.
  • n1 already knew the bottom road through n3, so it switches at once. The route changes at 3.000 s to 0-1-3-4-5, and back at 6.008 s after the repair.
  • The first packet on the detour arrives 43.6 ms after the break. That is exactly the bottom road's delay: 2 + 15 + 15 + 2 = 34 ms travel, plus 9.6 ms sending.
  • Only 2 packets lost: they were already on the wire when it broke. All 375 packets sent during the 3-second break were delivered (3 s × 125 per second = 375).
  • After the repair, throughput was 101.9% of before. Fully back to normal.

Story B2: the same break, but nobody reacts

  • Static routes never change, so n1 keeps sending into the broken link. 0 of 375 packets sent during the break arrived.
  • 377 packets lost: 375 lost_at_node (silently thrown away at n1, found only by following packet IDs) + 2 dropped_link_down (on the wire when it broke).
  • A 3.024 s delivery gap, from 3.0096 s to 6.0336 s. Nothing arrived until the link was repaired.
  • No routing messages and no route changes.
REMEMBER: B1 VS B2

Same failure. Smart routing: 2 packets lost, 43.6 ms to recover. Fixed routing: 377 packets lost, 3.024 s of silence. Routing decides whether a failure is a hiccup or an outage.

Story C: the traffic jam

  • From 3 to 6 s, 1 + 1.5 = 2.5 Mb/s tries to fit into the 2 Mb/s n1→n2 link (125% of what it can carry).
  • The queue at n1→n2 fills to its 20-packet limit at 3.30 s.
  • Delay of our flow: 33.6 ms before → 102.75 ms during (max 109.6 ms) → 35.24 ms after. A full queue of 20 packets × 4 ms each adds about 80 ms of waiting.
  • 170 packets dropped by the full queue: 117 from our flow, 53 from the extra flow. Loss during the jam: 30.93%.
  • The queue emptied 0.143 s after the extra flow stopped. The 357 packets sent after that had 0% loss and 33.6 ms delay, so the result is recovered.
  • No route change: DV only looks at link cost, not at how busy a link is.

26Part 4: the transport lab (TCP, UDP, TLS)

This part lives in communication/ and security/. Everything uses real sockets on 127.0.0.1.

A socket is the program's "phone line" to the network. One program opens a server socket and waits; another opens a client socket and connects.

Framing: putting messages in labelled boxes

TCP delivers a continuous stream of bytes, not separate messages. One message might arrive in three pieces, or two messages might arrive stuck together. So every message is put in a frame:

| type (1 byte) | length (4 bytes) | the actual data |

The receiver reads the length first, then keeps reading until it has exactly that many bytes. Frame types: MSG, FILE_META, FILE_CHUNK, FILE_END, ACK, ERROR, BYE. Frames over 16 MiB are refused.

THINK OF IT LIKE

Water through a pipe has no gaps between "messages". So you write "the next 500 ml is one message" on a label first, and the receiver fills a jug until it has exactly 500 ml.

The TCP vs UDP test

The same 1,000,000 bytes are sent 3 times with TCP and 3 times with UDP (1024-byte pieces). Stored result: TCP setup took 1.785 ms on average; TCP delivered everything with matching SHA-256; mean throughput TCP 3067.1 Mb/s vs UDP 840.4 Mb/s; all UDP pieces arrived.

DO NOT SAY "TCP IS FASTER"

These are loopback numbers on one laptop. TCP was handed 64 KiB chunks at a time, while UDP sent small 1024-byte pieces one by one. The app itself says the result depends on the computer, piece size and buffers, and that neither protocol is faster in general.

The UDP receiver

Each UDP piece carries a header: a magic word RRQU, a run ID, a sequence number, the total count and the send time. The receiver counts duplicates, out-of-order arrivals, and missing sequence numbers as ranges (like "50-54, 120, 199"). If nothing arrives for 1.5 s (the idle timeout), it stops and reports what is missing. UDP itself does nothing to fix losses, and RouteResQ deliberately adds nothing either; it only measures.

The TLS test

The project makes its own small, labelled set of certificates (a lab PKI) in results/certs/:

CertificateWhat it is for
Lab CAThe "trusted authority" the client believes in.
Valid serverFor localhost, signed by the lab CA. Should work.
Rogue serverSigned by an "Untrusted Rogue CA". Should be rejected.
Wrong hostSigned by the lab CA but made for wrong-host.example. Should be rejected.

The client trusts only the lab CA, needs TLS 1.2 or newer, and checks both the chain and the host name. Stored result of a good transfer: TLS 1.3, cipher TLS_AES_256_GCM_SHA384 (256-bit), and a 262,144-byte file with the same SHA-256 on both sides. Keys use the P-256 curve with SHA-256 signatures, valid for 30 days. No home-made cryptography is used anywhere.

26aPart 4b: a real upload while a link breaks

This lives in netlab/ and on the Upload test page. It is the newest experiment.

The question: you are uploading a file and, halfway through, a cable breaks. Does the upload take a detour, freeze until the cable is fixed, or fail and start again?

We build a tiny network inside a container: a client, a server and a router. The client and server have a direct main road (the primary link), and a longer detour through the router (the backup path). We upload a real 2 MiB file. When the server has received 30% of it, we cut the main road for 3 seconds. We do this three times with the same file and settings:

35What it cannot do, and what comes next

Limits (say these honestly)

  • Live checks only see what devices choose to answer. Routers and firewalls often block ping or traceroute, so a live cause is at best "Likely".
  • With only 4 pings, one lost ping changes loss by 25 points. Use more pings for loss studies.
  • Windows shows very fast pings as <1ms (stored as 0). Only English command output is understood.
  • NS2 results describe our model, not a real network. NS2's DV reacts instantly; real protocols such as RIP are slower.
  • Both NS2 flows are UDP, so scenario C does not show TCP slowing itself down.
  • Loopback has no real distance, and its speed depends on the laptop.
  • RouteResQ explains recovery; it does not fix real networks.
  • Not included on purpose: packet capture (Wireshark), intrusion detection, machine learning, automatic repair, custom crypto.

Next steps

Bigger maps, link-state routing with realistic timers, experiments between two real lab PCs, trends over many live runs, and DNS and MTU failure drills.

37Questions with easy answers

What does RouteResQ do, in one line?
It finds why a network failed, what that did to the traffic, and whether service came back, and it says honestly how sure it is.
What happens to an upload when a link breaks?
With a backup route the server paused only 0.07 s and the same connection kept going on the backup path. Without one it froze for 3.29 s until the link came back. Every file matched its SHA-256.
Why not just use ping?
Ping only shows a symptom. "No reply" could mean the computer is off, the path is broken, or ping is simply blocked. RouteResQ combines DNS, gateway, ping, traceroute and TCP checks to tell these apart.
What is the difference between a symptom and a cause?
A symptom is what you see (100% loss). A cause is why it happened (a broken link). Many causes can give the same symptom.
How does the project decide a live cause?
17 if-then rules turn the results into findings and possible causes. If exactly one cause fits all the evidence, it is "Likely". If several fit, it is "Not confirmed", and the checks that would separate them are listed.
Why can a live failure never be "Confirmed"?
Because we did not cause it. We only know the true cause in NS2 and the drills, where we created the fault ourselves.
Why no machine learning?
There is no labelled data of real failures to train on, and rules can be checked: every answer has a rule trace.
Why no percentages like "90% sure"?
There is no real way to calculate such a number here. It would be made up, so we use clear words instead.
What is the gateway check for?
If the gateway answers but the destination does not, the problem is beyond your own network. If the gateway fails too, the problem is close to you.
Why does 192.0.2.1 say "Not confirmed"?
The gateway worked, the path went quiet after hop 2, ping and TCP got nothing. The host could be off, the path could be broken, or a firewall could block probes. All three fit, so we do not pick one.
What is NS2 and why use it?
A network simulator from our course. We can break a link or overload it at an exact time, so we know the cause and can measure the effect on every packet.
Why is normal delay exactly 33.6 ms?
24 ms of travel on the wires (2 + 10 + 10 + 2) plus 9.6 ms to push an 8000-bit packet onto each link (0.8 + 4 + 4 + 0.8). No queueing.
Why are B1 and B2 so different for the same failure?
In B1, DV routing warns all routers at once and n1 switches to the backup road in 43.6 ms; only 2 packets are lost. In B2, static routes never change, so n1 keeps sending into the broken link: 377 lost and a 3.024 s gap.
How did you find losses in B2 when NS2 wrote no drop lines?
We follow every packet by its unique ID. 375 packets reached n1 and were never seen again while the link was down, so they are marked lost_at_node.
How do you avoid counting a packet many times?
"Sent" is counted only at the source node, and "received" only at the destination. Router events only build the path.
How do you prove congestion in scenario C?
2.5 Mb/s is pushed into a 2 Mb/s link, the queue hits its 20-packet limit, 170 packets are dropped on a working link, and delay rises from 33.6 to 102.75 ms. After the queue empties, loss is 0% and delay is normal again, so it recovered.
Why did the route not change in C?
DV routing looks only at link cost, not at how busy a link is, so it does not move traffic away from a jam.
Why does TCP look faster than UDP in your results?
It is a loopback test on one laptop. TCP was given 64 KiB chunks; UDP sent small 1024-byte pieces one by one. The app itself says neither protocol is faster in general.
What does the TLS test prove?
The certificate is signed by the trusted lab CA, the name matches localhost, TLS 1.3 was used, and the file's SHA-256 matched on both sides, so it arrived unchanged.
What is framing and why do you need it?
TCP is a stream of bytes with no message borders. Each message gets a small header with its type and length, so the receiver knows exactly where it ends.
How do you stop misuse of the tool?
Only allowed destinations, no shell, only 7 programs, input starting with "-" refused, and the public app blocks private addresses and new hosts.
What happens in the demo if NS2 is not installed?
It uses the newest saved runs, labels them "stored", and the report says so.
How do you know the code is correct?
186 tests: real saved command outputs, small traces with known answers, real NS2 runs, real sockets and every page of the website.
What would you add next?
Bigger maps, link-state routing with real timers, tests between two lab PCs, trends over many runs, and DNS/MTU drills.

The problem. "The site is not opening" has many possible causes. Tools like ping show symptoms, not causes, and can mislead.

The idea. Collect real evidence, apply clear rules, and say honestly how sure we are, in words, never fake percentages.

Part 1, live checks. DNS, gateway ping, ping, traceroute and TCP on allowed destinations only, run safely without a shell.

Part 2, rule engine. 17 if-then rules give findings, possible causes with evidence for and against, contradictions, and a rule trace. Live causes are at best "Likely".

Part 3, NS2. A 6-node map with a main and a backup road. A: healthy, 33.6 ms. B1: link breaks, DV reroutes in 43.6 ms, 2 lost. B2: same break with static routes, 377 lost, 3.024 s gap. C: 2.5 Mb/s into 2 Mb/s, queue full, 170 drops, delay 102.75 ms, then recovered. Packets are followed by ID, which finds 375 silent losses in B2.

Upload test. A real 2 MiB upload with the link cut at 30%: backup route = 0.07 s pause, no backup route = 3.29 s freeze; same connection, file matched.

Part 4, transport lab. Real TCP, UDP and TLS on loopback. Framing for TCP, gap detection for UDP, TLS 1.3 with certificate and SHA-256 checks, and six drills that break and repair the connection (6/6 recovered).

Joining it up. The root-cause register: 16 rows, 13 failures with a cause, each with a status: Confirmed (injected), Likely, Not confirmed or No failure detected.

Built with Python, Streamlit, Plotly and NS2 2.35; 186 tests; live at routeresq.streamlit.app.
