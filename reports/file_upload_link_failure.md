# File upload under link failure

_Generated by RouteResQ (`python -m netlab.runner --report`) from the stored run data._

**Question.** If a network link goes down halfway through a file upload, does the upload continue on a backup route, stall until the link returns, or fail and need a retry?

**Source.** Recorded run: captured locally on 2026-11-19 with the docker backend (real TCP upload in an isolated Linux test network) and replayed here from saved data.

## Set-up

```
                primary link (direct, 5 ms each way)
   client cp0 --------------------------------- sp0 server
10.98.0.1 cb0 --- rc0 [router] rs0 --- sb0          10.99.0.1
            backup path (two hops, 10 ms each way per hop)
```

* Three Linux network namespaces joined by veth links, built inside the lab container; the host's network is not touched. The TCP connection runs between the two service addresses, so it can survive a change of path.
* The client uploads the real file bytes with RouteResQ's framing (FILE_META, FILE_CHUNK, FILE_END) and the server replies with its SHA-256. The client is paced so the upload is still running at the fault.
* File: `routeresq-sample-2MiB.bin`, 2,097,152 bytes, SHA-256 `21520867e30de924...`. Pacing 512 KiB/s in 8 KiB chunks; socket timeout 10 s; up to 1 retry (a new TCP connection that re-sends from byte 0; resuming from an offset is not supported).
* Fault: both ends of the primary link are taken down once the **server** has received 30% of the file, and brought back 3 s later.

| Run | What differs |
|---|---|
| Healthy baseline | The primary link stays up for the whole upload. |
| Link failure · backup route | The primary link goes down mid-upload. A backup route through the router is pre-installed with a higher metric (a floating static route), so forwarding can switch to it. |
| Link failure · static forwarding | The same link goes down at the same point. The backup path is still connected and forwarding, but there is no route to it, so forwarding cannot switch. |

No routing protocol runs in the test network. The backup route in the failover run is a pre-installed floating static route (controlled failover), not distance-vector routing.

|---|---|---|---|---|---|---|---|
| Healthy baseline | Completed normally | 4.04 s | 0.017 s | no | yes | no (336 B) | match |
| Link failure · backup route | Continued on the backup path (same TCP connection) | 4.07 s | 0.071 s | no | yes | yes (1,496,468 B) | match |
| Link failure · static forwarding | Stalled until the link returned, then resumed (same TCP connection) | 4.72 s | 3.287 s | no | yes | no (250 B) | match |

_Stall duration = the longest interval in which the server's count of received file bytes did not increase. In the fault runs only pauses ending after the link went down count; in the baseline the whole transfer counts._

_Backup path used = at least 16 KiB more left the client's backup interface while the primary link was down (interface byte counters, sampled every 50 ms)._

No fault was injected. The server received all 2.00 MiB in 4.04 s on the primary link; its longest pause was 0.017 s. The SHA-256 fingerprints matched.

The primary link went down after the server had received 30% of the file (0.60 MiB). The server stopped receiving bytes for 0.07 s. The same TCP connection then continued on the backup path (1.43 MiB left through the client's backup interface during the outage), and the file matched (SHA-256).

## Limits

* The test network is three namespaces on one Linux kernel with emulated delays; it shows TCP and kernel forwarding behaviour, not the timing of a real WAN.
* Failover is a floating static route that the kernel uses as soon as the primary interface goes down. A routing protocol (OSPF, RIP) would add its own detection and convergence time.
* A retry re-sends the whole file; the client cannot resume from a byte offset.
