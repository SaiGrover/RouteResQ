01The 1-minute pitch

Memorise this. It is your opening answer to "Tell us about your project".

SAY THIS
RouteResQ is a network failure lab. When a connection fails, normal tools like ping only show the symptom. RouteResQ finds the cause. It runs real DNS, ping, traceroute and TCP checks, and seventeen rules turn the output into possible causes, each marked confirmed, likely, possible or not enough evidence. We also run the real NS2 simulator: we break a link or overload it on purpose and measure, packet by packet, what happened to the traffic and whether it recovered. And we test real TCP, UDP and TLS connections, breaking them in six controlled ways. A root-cause register brings it all together: one row per failure, with its cause and an honest status. It is built in Python with a Streamlit interface, it is deployed online, and it has 159 automated tests.
Key ideaIf you remember one sentence: we never guess the cause, we show the evidence and say how sure we are. A live cause can be Likely at best; only a fault we injected ourselves is Confirmed.

02The problem and our idea

What is wrong today

  • One symptom, many causes: "the site is timing out" can be a DNS failure, a host that is down, a broken path, congestion, a closed port or a bad certificate.
  • Tools show symptoms, not causes: ping, tracert and nslookup each see one piece, and you read the raw output by hand.
  • Tools can mislead: routers ignore ping, firewalls block traceroute, and a TCP connection can work while ping fails.
  • False confidence: people pick one cause and state it as fact, with nothing to back it up.
  • Learnt in pieces: diagnostics, routing simulation and socket programming are separate lab exercises, so nobody connects "what failed" to "what happened to the traffic".

Our solution in three parts

  • Diagnose live failures with real commands and a rule engine that lists causes with evidence for and against.
  • Measure the impact of failures we inject in NS2: loss, delay, throughput, route changes and recovery, from the simulator's own trace.
  • Prove it with a root-cause register and reports, where every number links back to the measurement that produced it.

03The three kinds of evidence

The most important design idea. The three are kept apart and labelled on every page, so a simulated cause is never presented as the cause of a live problem.

EnvironmentWhat it isBest possible status
Live networkReal ping, traceroute, DNS and TCP on the machine running RouteResQ. We did not cause the failure, so we can only infer it.Likely
NS2 simulationThe real ns-2.35 simulator. We take a link down or add traffic at an exact time, so we know the cause.Confirmed (injected)
Real socketsTCP, UDP and TLS between two programs on this computer (loopback). We create each fault ourselves.Confirmed (injected)
  • There are no confidence percentages. Nobody can honestly say "73 % sure" about a network fault, so we use words.
  • No machine learning, no packet capture, no made-up data. Every chart is drawn from a stored result.

04The full flow, step by step

Follow one real run of our guided demo. The five stages are also the navigation bar at the top of the app: Detect → Diagnose → Analyse impact → Observe recovery → Report.

1

Pick the destinations USER

We choose three: 8.8.8.8 (Google DNS, should work), nonexistent.invalid (a name that can never exist) and 192.0.2.1 (an address reserved for documentation, with no real computer behind it). Each is first checked against the allowed list.

2

Detect: run real checks LIVE

For each destination: find the default gateway, look up the name in DNS, ping the gateway, ping the destination, run traceroute, and optionally try a TCP connection. Every command and its raw output is saved.

3

Diagnose: apply the 17 rules RULES

The output is turned into facts ("0 of 4 replies", "last hop that answered was hop 2"). Each rule checks one condition and records whether it fired and why. The result: findings, candidate causes with evidence for and against, and the checks that would confirm them.

4

State the cause and how sure we are REGISTER

nonexistent.invalid: DNS says "no such name" and the gateway works, so only one explanation fits → Likely. 192.0.2.1: no replies, path goes silent after hop 2, three explanations still fit → Not confirmed, with the checks that would decide.

5

Analyse impact: run NS2 NS2

We run the same six-node network four ways: healthy, a link failure with distance-vector routing (B1), the same failure with static routing (B2), and congestion (C). Each run writes a trace file with every packet event.

6

Rebuild every packet ANALYSIS

Each of the 1,001 packets is followed by its unique id: when it left, which routers it crossed, and whether it arrived, was dropped, or silently vanished. From that we compute loss, delay, throughput, route changes and gaps.

7

Observe recovery NS2

B1 rerouted: the first packet over the backup path arrived 43.6 ms after the failure. B2 was interrupted for 3.024 s until the link came back. C recovered once the queue drained. Recovery is only claimed when the trace shows it.

8

Transport lab SOCKETS

Send real data over TCP and UDP, send a file over TLS and check its SHA-256 on both ends, then run six failure drills: no server, silent server, reset mid-transfer, missing UDP packets, untrusted certificate, wrong host name. Each drill is then fixed and re-tested.

9

Report REPORT

The root-cause register lists all 13 subjects; 11 have a stated cause. The demo report says exactly which results are fresh, which came from stored runs, and which failed.

How every failure gets its cause status in the root-cause register

The four statuses, in one line each

  • Confirmed (injected) we caused it on purpose (NS2 or a drill) and the trace or error shows its effect.
  • Likely live network: exactly one explanation fits all the evidence.
  • Not confirmed live network: several explanations fit; we list them and the checks that would separate them.
  • No failure detected nothing to explain.

Storage

How a request travels

The most important rule of the code: the web pages contain no networking logic. Think of a lab:

  • Page = the lab bench where you press the button and read the result.
  • Backend module = the instrument: it runs the real command, simulator or socket.
  • Results folder = the lab notebook: every measurement is written down before anyone draws a conclusion.
  • Report = the write-up, built only from what is in the notebook.

Because of this, the same backend runs from the website, from the command line and from the tests, and gives identical numbers.

08Diagnosing a live failure: the rule engine

Expect many questions here. Learn the evidence levels, a few key rules and the worked example.

The safety check before anything runs

  • Only allowed destinations: a fixed list (8.8.8.8, 1.1.1.1, example.com…), the two reserved test targets, your own computer (loopback) and, locally only, your own network.
  • Input starting with - is refused (it would be read as a command option), and so is anything that is not a valid name or address.
  • Only seven programs can ever run (ping, tracert, traceroute, tracepath, route, ip, ipconfig), always without a shell, always with a timeout.

Four evidence levels

LevelMeaning
confirmedDirectly seen in the output, e.g. "0 of 4 replies". An observation, not a cause.
likelyThe one explanation that fits all the evidence.
possibleFits the evidence, but other explanations cannot be ruled out.
insufficient evidenceNot enough data, e.g. fewer than 3 replies to judge latency.

The rules you should know

RuleFires whenResult
R-DNS-01The name cannot be looked upDNS failure
R-REACH-010 ping replies (unless TCP or traceroute show the host is up)Unreachable
R-REACH-02A router or the OS says "unreachable" / "no route"Unreachable
R-TCP-01The TCP connection times outUnreachable
R-LOSS-01 / 02Loss of 5 % or more / 100 % lossPacket loss
R-LAT-01 / 02Average RTT over 150 ms / RTT spread over 30 ms, with 3+ samplesHigh latency
R-BASE-01…04RTT, loss, spread or throughput clearly worse than this destination's normalCompared with baseline
R-CONG-01Two or more congestion signs togetherPossible congestion
R-ROUTE-01Traceroute stops early and ping fails and TCP does not answerPossible routing issue
R-ROUTE-02A hop answers from a different address than last timeRoute changed
R-OK-01Name resolves and the host answersHealthy
  • Why two signs for congestion? One slow ping has many explanations (distance, a slow router, a busy server). Two independent signs together are needed.
  • Every rule is listed in the rule trace, with the reason it fired or did not. That is how an examiner can audit any conclusion.
  • Contradictions are shown, not hidden: "ping failed but TCP connected" means the host is up and ping is being blocked.

Worked example: 192.0.2.1 (Not confirmed)

1

Symptom

The destination did not answer any ping (0 of 4), and the TCP connection timed out.

2

Measurements

The gateway 192.168.1.1 answered 4 of 4, so our own network works. Traceroute: the last hop that answered was hop 2 (10.240.12.49), then 8 silent hops.

3

Possible explanations

The host is down; part of the path after hop 2 is broken; or a firewall blocks ping and traceroute. All three fit the evidence.

4

Limits and next checks

No router sent an explicit error, so we cannot pick one. Next: try a TCP port the host should serve, re-run traceroute later, ask the owner. Status: Not confirmed.

Why not just guess?A "timed out" result looks identical whether the host is off or a firewall drops our probes. Saying "Not confirmed, and here is how to find out" is the honest and useful answer.

09NS2: breaking the network on purpose

The second big area of questions. Learn the topology, the four scenarios, how packets are counted and the headline numbers.

Six nodes. Traffic normally takes n0–n1–n2–n4–n5. The backup path through n3 is longer and costs more, so it is only used when needed.

The four experiments

LabelRoutingWhat we inject
ADistance-vectorNothing. The healthy baseline every other run is compared with.
B1Distance-vectorLink n1–n2 goes down at 3 s and comes back at 6 s.
B2StaticExactly the same failure, but routes never change.
CDistance-vectorAn extra 1.5 Mb/s flow from 3 s to 6 s: 2.5 Mb/s pushed into a 2 Mb/s link.
  • Traffic: 1000-byte packets at 1 Mb/s, one every 8 ms, from 1 s to 9 s: 1,001 packets.
  • Phases: before = 1–3 s, during = 3–6 s, after = 6–9 s, the same in every scenario.
  • Distance-vector (DV) routers tell their neighbours how far each destination is and react when a link changes. Static routes are worked out once and never updated.

Counting packets correctly

  • NS2 gives every packet a unique id. We follow it across routers instead of counting lines, so a packet that crosses four links is still one packet.
  • Sent = first seen at the source. Received = arrived at the destination. Router events only add to its path.
  • Every packet ends with one fate: delivered, dropped at a full queue, dropped on a dead link, lost at a router without a trace line, lost on a link, or still in flight at the end.
loss % = lost ÷ (sent − still in flight) × 100
delay = arrival time − send time (average over delivered packets)
throughput = bits that arrived in the window ÷ length of the window

Worked example: why the healthy delay is exactly 33.6 ms

Each part of the path adds a fixed amount. Propagation is the link's delay; transmission is 8,000 bits ÷ link speed.

n0→n1: 2 ms + 0.8 ms
2.8 ms
n1→n2: 10 ms + 4 ms
14.0 ms
n2→n4: 10 ms + 4 ms
14.0 ms
n4→n5: 2 ms + 0.8 ms
2.8 ms

Total 33.6 ms, exactly what the trace measured for all 1,001 packets. The backup path has two 15 ms links instead of 10 ms, so it takes 34 + 9.6 = 43.6 ms. That is exactly the delay seen in B1 during the failure.

  • B1: the routers sent 14 routing updates in the half second after the failure (normally about 2.4) and switched to n1–n3–n4 at once. Only the 2 packets already on the broken link were lost; all 375 sent during the outage arrived.
  • B2: n1 kept sending into the dead link, so all 375 packets sent during the outage were lost, plus the same 2 already on the link.
  • C: the n1→n2 queue filled to its 20-packet limit, delay rose from 33.6 to 102.75 ms, and 170 packets overflowed (117 of ours). The queue emptied 0.14 s after the extra traffic stopped.

The finding we are proudest of

In B2, NS2 2.35 does not write a drop line for packets that reach a router with no working route. A simple "count the d lines" approach would report almost no loss. Because we follow each packet's id, we see 375 packets arrive at n1 and never appear again while the link is down, so we classify them as lost at node n1 and say where and why.

Why not trust the simulator blindly?The trace only records what NS2 chooses to log. Rebuilding every packet from its own events is what lets us account for every one of the 1,001 packets.

10The transport lab: TCP, UDP and TLS

  • TCP sends a stream, not messages, so we wrap each message in a frame: 1 byte type + 4 bytes length + the data. The receiver keeps reading until the whole frame has arrived (this handles "partial reads").
  • UDP datagrams carry a sequence number. The receiver reports exactly which numbers are missing, duplicated or out of order. We never resend anything: UDP loss is measured, not repaired.
  • TLS: the client trusts only our lab certificate authority and checks the server's name. The file's SHA-256 fingerprint must be equal on both ends. Our run used TLS 1.3 with AES-256-GCM.
  • TCP vs UDP on this computer: TCP 3,067 Mb/s, UDP 840 Mb/s, both delivered everything. We say clearly this is one machine's loopback result, not a rule that TCP is faster.

12Pitfalls we found and handled

Real traps in network data and in our own code, and what we did about each. Showing you understood these impresses examiners.

#The trapWhat we did
1Windows ping counts "Destination host unreachable" as a reply.We count only real echo replies and note the difference.
2B2's losses were invisible: NS2 writes no drop line for them.We follow each packet's id and classify them as lost at the router.
3A different traceroute hop limit could look like a route change.We compare hop by hop, only where both runs got an answer.
4Old analyses were shown after we improved a rule.The register re-analyses stored runs with the current rules.
5Stored NS2 runs carried Windows file paths that broke the online demo.Runs are located on disk, not by the saved path.
6NS2 runs from different computers sorted wrongly by folder name.They are sorted by the UTC start time saved inside each run.
7The online app kept running old code after an update.It reloads changed modules automatically.
8Congestion recovery could be judged while the queue was still emptying.We judge it on packets sent after the queue drained.
9The top navigation bar felt laggy.It navigates in the browser without re-running the page.

14Limitations and future scope

Be honest here. Admitting limits clearly is a strength in a viva.

Limitations

  • Live tools only see what devices answer. Blocked ping or traceroute hides part of the path, so live causes are Likely at best.
  • With 4 pings, one lost reply is 25 % loss. Use more probes for real loss studies.
  • NS2's distance-vector reacts almost instantly; real protocols like RIP take longer to converge.
  • Both NS2 flows are UDP, so scenario C does not show TCP slowing down under congestion.
  • Loopback has no real distance or loss; throughput depends on the computer.
  • Command output is read in English only, and RouteResQ explains failures but does not repair them.

Future scope

  • Larger topologies and link-state routing with realistic timers.
  • Experiments between two real lab computers over a switch.
  • Trend analysis of repeated live runs; DNS and MTU failure drills; bandwidth limits.

17Likely viva questions

Basics

What problem does RouteResQ solve?
Network tools show symptoms, not causes, and people guess. RouteResQ collects evidence from real checks, simulations and socket tests, states the cause of each failure, and says honestly how sure it is.
What makes it different from just running ping?
It combines DNS, gateway, ping, traceroute and TCP checks, applies traceable rules, reports contradictions, measures failure impact in NS2, and keeps every result as evidence in a report.
Why three separate environments?
Only when we create the fault (NS2 and the drills) do we know the true cause. Live failures can only be inferred. Keeping them apart stops a simulated cause being passed off as a live diagnosis.
Why no confidence percentages?
There is no honest way to calculate a probability for these guesses. A number like "73 %" would be made up, so we use clear words: confirmed, likely, possible, insufficient evidence.

Live diagnosis

How do you decide the cause of a live failure?
Seventeen rules turn the measurements into findings and candidate causes, each with evidence for and against. If exactly one cause fits all the evidence it is Likely; if several fit it is Not confirmed, with the checks that would decide.
Why can a live cause never be Confirmed?
We did not cause it, and our tools only see what devices choose to answer. Only an injected fault is Confirmed.
Ping fails but TCP connects. What do you conclude?
The host is up and ping (ICMP) is being blocked. We report it as a contradiction and mark the host reachable, instead of calling it down.
Why does congestion need two signs?
A single high RTT can come from distance, a slow router or a busy server. Two independent signs together, such as higher delay and some loss, are needed before we suggest congestion.
What is a baseline?
A healthy run you mark as "normal" for a destination. Later runs are compared with it, e.g. RTT more than 1.5 times and at least 20 ms higher.
How do you stop misuse?
An allow-list of destinations, refusing inputs that look like options, seven allowed programs, no shell, timeouts, and a stricter public mode on the website.

NS2 and routing

Why NS2?
It is the standard simulator in our course, it lets us inject a failure at an exact time so the cause is known, and its trace lets us measure every packet. We run the real simulator, not a mock.
Why do B1 and B2 behave so differently for the same failure?
With distance-vector routing the routers notice the failure and switch to the backup path within 43.6 ms, losing 2 packets. With static routing the route never changes, so everything sent during the 3 s outage is lost.
Why is the healthy delay exactly 33.6 ms?
24 ms of propagation (2 + 10 + 10 + 2) plus 9.6 ms to put an 8,000-bit packet on each link (0.8 + 4 + 4 + 0.8), with no queueing.
How do you avoid counting a packet several times?
We follow NS2's unique packet id. A packet is sent only when first seen at the source and received only at the destination; router events just extend its path.
How did you find losses NS2 didn't record?
375 packets arrived at n1 while its link was down and were never seen again. With no drop line, we still classify them as lost at n1 because we track every packet.
How do you prove congestion in scenario C?
2.5 Mb/s offered to a 2 Mb/s link; the queue reaches its 20-packet limit; 170 drops on a working link; delay rises from 33.6 to 102.75 ms. After the queue drains, loss is 0 and delay is back to normal, so we call it recovered.
What is a route change, in your analysis?
When delivered packets switch to a different path and at least 3 in a row stay on it, so one stray packet is never called a route change.

Transport and security

Why frame TCP messages?
TCP is a byte stream: one send can arrive in pieces and two sends can arrive together. A type and length header tells the receiver exactly where each message ends.
How do you detect UDP loss without adding reliability?
Each datagram carries a sequence number. The receiver lists the missing numbers, duplicates and out-of-order arrivals, and an idle timeout ends the run. Nothing is resent.
What does the TLS test prove?
The certificate chains to our trusted lab authority, its name matches localhost, TLS 1.3 with AES-256-GCM was used, and the file's SHA-256 is the same on both ends, so it was not altered.
Is TCP faster than UDP?
Not in general. On our machine TCP measured 3,067 Mb/s and UDP 840 Mb/s on loopback, but that depends on packet size, pacing and buffers. The app says so itself.
Why not use ML for diagnosis?
We have no labelled dataset of real network failures, and the brief excludes it. Rules are explainable: every conclusion points to a rule and its evidence.

Code, testing and process

How is object-oriented design used?
Measurements are data classes combined into one DiagnosticRun; a CommandRunner interface lets tests swap in a fake runner; custom exceptions extend Python's built-in ones; a Scenario checks itself when created; the TCP server is a context manager that always closes its socket.
How did you test it?
159 automated tests: parsers with real captured output, rules with fake measurements, traces with known answers, real NS2 runs, real sockets, real commands and every page of the app.
What happens if NS2 is not installed?
The guided demo uses the newest saved NS2 runs, marks them as stored, and the final report says so. It never claims fresh results it did not produce.
What would you do with more time?
Bigger networks, link-state routing with realistic timers, experiments between two real lab computers, trend analysis of repeated live runs, and DNS and MTU failure drills.
